Tone feature check

One question: can a browser render A-Z+T's tone letters the way the app must show them — joined into contours, and (where wanted) without staves? Judge it by eye; nothing here knows what your orthography should look like. This is a companion to the Keyman input check: that one was about typing, this one is about rendering.

Kill condition (from agenda/webview_when_to_finish.md, Step 2): if adjacent tone letters do not join, and cv92 does not hide staves, and a dropped -tstv font file does not do it either, then tone pages cannot be ported to a webview and the whole item shrinks to non-tone pages. Any one of the three working is enough to proceed.

4. The matrix

Columns are OpenType feature settings, applied with CSS font-feature-settings — something tkinter cannot express at all. Per SIL's own feature page, cv92 hides tone-contour staves, cv91 gives tone numbers, cv90 is Chinantec tones; both cv91 and cv92 are marked "not supported in TypeTuner Web", and cvNN variants are off by default — which is why the "no features" column should look like the app's default.

—

Read the box above before concluding anything. It reports what the browser actually computed for one cell. If font-feature-settings comes back normal, or the resolved family is not the one you picked, then the CSS never reached the text and the rendering below is meaningless — that is a bug in this page, not an answer about the font.

What "joined" means: in the contour rows, ˥˩ should render as one falling contour on a shared stave, not as two separate letters sitting next to each other. That is font behaviour a HarfBuzz-based shaper applies; both WebKitGTK and Chromium are HarfBuzz-based, so a difference between them is itself diagnostic.
